# 平台契约与兼容开发约定

## 1. 目的与适用范围

BioWorkflowManage 是通用分析底座。OKbox、血液肿瘤入口及未来调用方遵守同一平台契约，
不要求平台逐一适配客户业务，也不以绑定某个上游仓库或特定客户端为兼容性的定义。

本约定约束日常开发、接口扩展、问题修复和跨项目联调，**不要求现在发布软件 Release**。
平台和上游可以继续增加功能；正式 Release 待运行、接入和运维验证充分后另行决定。
契约文档修订号、分析产品版本和软件 Release 是不同概念。

## 2. 契约唯一来源

| 内容 | 权威入口 |
| --- | --- |
| 面向接入者的调用方法、双方责任与最小验收 | [分析服务接入指南与契约](23-analysis-service-integration-guide.md) |
| 路径、参数、字段、枚举、权限 scope、回调结构 | [Integration OpenAPI](../schemas/integration-openapi-v1.json)，在线 `/api/v1/integration/openapi` |
| 幂等、任务生命周期、输入和结果交付语义 | [集成接口说明](14-integration-api-and-mcp.md) |
| 可选的数据复制完成协议 | [rawdata 完成标记](rawdata-ready-marker.md) |
| 具体流程的输入、输出、引擎与资源绑定 | 显式发布的 `analysis_code + contract_version` 及其不可变契约 |
| 向后兼容检查依据 | [历史 OpenAPI 基线](../schemas/compatibility/README.md)与平台行为测试 |

本文件规定如何变更契约，不取代接口字段定义。文档、OpenAPI 和实现不一致时属于需要核实的
缺口，不能任意选择一方作为借口破坏已支持的行为。先补充证据和回归，再同步修正。
未文档化的实现细节不自动成为新上游可以依赖的公共接口。

## 3. 平台与上游的责任

**平台负责**：产品目录、受管输入和资源预检、幂等投递、排队执行、状态/错误、结果清单、
受保护下载、可选导出及签名通知。MiniWDL 与 Nextflow 的执行差异留在内部适配器。

**上游负责**：用户和样本业务、患者/订单信息、字段映射、任务与业务记录关联、结果解析和展示。
服务凭据留在上游后端；不共享平台数据库，不写 `AnalysisRun`，不依赖内部 ORM、运行目录或
管理页面接口。大型 FASTQ/结果不塞进投递 JSON 或 Webhook。

上游固定分析产品版本，不动态选择“最新版”，不通过通用提交接口指定任意脚本、镜像或引擎参数。
平台优化调度不代表升级已选流程。改变算法、参数默认值、资源版本、输出列或分析含义时，发布新的
分析产品版本并保留历史运行证据；不得以“Bug 修复”为理由覆盖同版本产品或旧结果。

## 4. 日常兼容规则

1. 旧契约描述的合法请求仍可使用；不悄悄增加必填字段、缩小取值范围或改变省略参数时的行为。
2. 不删除或改名旧响应字段，不改变类型、单位、枚举、错误含义、分页规则、下载或回调语义。
   新增状态也需要检查旧调用方如何处理，不能默认它一定兼容。
3. 新能力优先独立接口或显式可选参数；未启用时保留旧行为。不因新增一个上游而全局强制新协议。
4. 响应允许扩展的对象，上游应忽略未知可选字段；`additionalProperties: false` 的闭合对象仍按
   声明严格处理。未知状态/错误应显示可诊断的兜底信息，不能猜成成功或无条件重试。
   上游不发送未声明的请求字段，不以中文错误提示文本代替稳定错误码判断。
5. 接受任务后固定输入、流程及契约证据。异步通知可能重复或乱序，上游按事件身份和状态版本处理；
   通知失败、结果交付失败和上游入库失败不反向改写分析执行结论。
6. 认证、scope、环境变量默认值、资源挂载和结果保留策略也可能影响兼容性；仅 OpenAPI 未变化
   不代表没有公共行为变化。新增功能不得关闭现有安全和输入完整性检查。
7. 严重安全或结果正确性问题可以要求紧急阻断受影响功能，但必须明确影响、原因、恢复/迁移办法，
   保留审计和历史证据；不能为维持表面兼容继续默默产生错误结果。

例如：`include_unready=true` 和顶层 `rawdata_readiness` 是显式选择的复制完成协议。
默认目录查询保持旧配对过滤和返回形状；没有携带快照的已有任务沿用原规则。
采用新协议的调用方使用 `readiness.submission_allowed`，不能把旧 `status=ready` 当作复制完成。

## 5. 变更分类与协作流程

| 分类 | 示例 | 必需动作 |
| --- | --- | --- |
| internal | 内部重构、对外行为不变的性能优化、纯 UI | 说明无公共影响，运行相关已有测试 |
| additive | 独立新接口、显式可选能力 | 同步 OpenAPI/说明/正反样例，保留并验证旧调用 |
| migration | 必填字段、默认行为、状态/错误/结果含义变化 | 先提出迁移方案，旧契约与新能力并行，明确接入与退场证据 |

分类按行为而不是提交标题；`fix` 不自动等于兼容。只影响内部实现的工作不强制新建协调 Issue
或增加多轮评审。涉及迁移或多个仓库的工作使用 [契约变更模板](../.github/ISSUE_TEMPLATE/integration-contract-change.md)，
记录：改变什么、旧行为如何继续、谁受影响、验证方式和接入顺序。

变更步骤：

1. 在平台仓库定义或补齐契约、示例和兼容分类；上游按这份定义实现，不各自维护相互冲突的协议。
2. 平台先提供保留旧行为的可选新能力，并通过旧基线和相关行为回归。
3. 上游显式采用新能力，完成投递、状态和结果解析验证；新调用方只需满足同一验收清单。
4. 记录哪些能力经过验证、哪些仍待完成。不能把平台测试通过写成某个上游或临床流程已验收。
5. 旧契约默认继续保留。真要退场，必须另行明确支持范围、通知/迁移窗口、调用方确认及数据处理，
   不因增加新基线或新上游就自动删除旧接口。新主版本也不能自动移除仍使用中的 v1。

需求和代码通常经 PR 进入 `main`；本约定不自动授权 Git 写操作或生产部署。
无需为每个客户维护核心代码分叉，也不必等软件 Release 才能形成契约基线。

## 6. 自动检查与验收

本仓库复用现有工具链，不引入独立契约服务器：

```bash
uv run python scripts/validate_contracts.py
uv run pytest backend/tests/test_integration_compatibility.py \
  backend/tests/test_integration_api.py backend/tests/test_rawdata_readiness.py \
  backend/tests/test_reference_connector.py
```

- 历史基线只增不改。当前契约须通过所有 v1 基线；PR 检查还核对目标分支中的存档未被改写/删除。
- 结构门禁保守保护旧路径、字段、约束、状态、scope、默认值与回调，允许明确支持的增量扩展。
  它不是完整的 JSON Schema 子集证明器；拒绝了确实兼容的改动时，先增加专项证据和检查器支持，
  不能刷新旧基线或放宽历史行为断言绕过。
- 行为回归覆盖固定产品、幂等与超时找回、隔离权限、异步状态、结果完整性、签名/重复通知和可选协议。
  Reference Connector 是通用接入示例，不代表平台必须服从它的私有实现。
- 引擎、流程参数或资源适配变化，另跑受影响的真实小数据流程；结构检查和 mock 不证明生信结果正确。
- 只改规范/说明时运行链接与契约检查即可；无需为每个文档修改执行完整生产流程。

新上游的最小接入验收：用最小 scope 的独立 Service Account 读取固定产品，预检并幂等提交，
确认重复请求不重复执行，正确处理成功/失败与输出不完整，读取并校验结果；启用回调、导出或
复制完成协议时，再覆盖对应能力。输入采用脱敏或合成测试数据，不把密钥或患者信息写进样例。

本次规范落在平台仓库；不代表已经修改任何上游仓库或获得其负责人的确认。
上游建立开发约定时可引用以下内容，而不是复制一份容易漂移的 OpenAPI：

> 分析能力以 BioWorkflowManage 的《分析服务接入指南与契约》、Integration OpenAPI 及固定分析产品为准。
> 上游负责业务映射和结果消费，不访问分析数据库或内部运行路径；新能力显式启用。
> 接口需求先在平台契约中定义，再开发适配并通过接入验收；不得要求平台默默破坏旧调用。

引用时记录已经验证的契约修订/平台提交即可，不要求先有正式软件 Release。
